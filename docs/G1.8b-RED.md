# G1.8b — THE RED TEST, captured before the fix

**This file is the proof that the test discriminates.** A green test after the fix means nothing
unless the same test was red first. Everything below was captured on the tree as it stood before a
single line of the fix was written.

## The defect under test

A **syscall override is a plain synchronous call on real hardware**: the guest issues `syscall`, the
kernel calls the installed handler, the handler returns, `$v0` holds the result. The guest's caller
frame is never unwound, because nothing unwinds it.

The runtime instead deferred *every* override to `EeScheduler::invokeCurrent`, which **throws
`EeDispatcherTransfer`**. `runtime/ee_scheduler.h` documents that signal as:

> the EE equivalent of a longjmp to the dispatcher. It is not an error and must only be caught at
> `EeScheduler::run()`.

`tools/harness/vulcan4_harness.cpp` is **not** `EeScheduler::run()` — it is its own driver loop, and
it catches the signal itself. So the throw leaves the guest's callee frame, the queued invocation is
never serviced by anything, and the guest never receives the handler's result. That is G1.8's
measured boot signature: `$s2`/`$s3` reset to zero every third iteration of GT4's convergence loop.

## The two test shapes

Both were asked for; both are present, and both are red.

| Shape | Test | Asserts |
|---|---|---|
| **Exception** | `G1.8b: an overridden syscall does not throw out of the guest's frame` | `EeDispatcherTransfer` never escapes; handler runs once; caller resumes; `$v0` correct; `$s2`/`$s3` intact |
| **Counter** | `G1.8b: the guest's s-registers are not reset every third overridden syscall` | six overridden syscalls from one guest frame, the frame intact after **every** one — the "every third iteration" shape GT4 actually showed |

The driver helper `driveGuestLikeTheHarness` deliberately reproduces the **harness's** drive pattern
(call the generated function for `ctx.pc` inline; on the transfer signal, re-enter at `ctx.pc`) and
**not** `EeScheduler::run()`. That is the point: the scheduler's own loop was already correct, so a
test against it would have been green before the fix and would have proved nothing.

That is the same latch the boot showed: `0x83` served by the guest's own override once, then by our
builtin forever after.

## GREEN output, after the fix

The contract was **restated once during the fix**, and honestly, so read the sequence rather than
just the endpoints.

**Attempt 1 — make the override synchronous.** The first hypothesis was that the transfer should not
cross the guest frame at all, since a syscall is an ordinary call on hardware. That is **wrong, and
the suite said so**: `a syscall invocation can block and resume without losing its base context`
**segfaulted**. A handler is allowed to block, and a block parks whichever thread it runs on; run
inline that is the *caller*, so `invokeCurrent()` then had no current thread to own the invocation
and dereferenced null. The attempt was reverted and the reason is recorded in the code.

**Attempt 2 — the driver must service what the guest queued.** `EeDispatcherTransfer` is correct and
must stay: it is the documented way to reach the dispatcher. What was missing is the driver's
*obligation* on catching it. A driver that is not `EeScheduler::run()` — the harness — must hand the
signal to the scheduler so the queued invocation actually runs, and must drive the **runtime's**
context (`runtime.cpu()`), which is the object the scheduler publishes back into.

```
  [Run]: G1.8b: a non-scheduler driver honours an overridden syscall without losing the guest frame  [Passed]
  [Run]: G1.8b: the guest's s-registers are not reset every third overridden syscall  [Passed]
Total Tests: 449
Passed: 449
Failed: 0
```

The four pre-existing override contracts all still pass, which is the point of keeping the deferred
path: `SetSyscall override runs as a scheduler invocation`, `... preserves KSEG argument sign
extension`, `... preserves upper 64 bits when writing 32-bit args`, `an override that branches to an
invalid PC completes without builtin fallback`, `reentrant override invokes the underlying builtin
inside its invocation frame`, and `a syscall invocation can block and resume without losing its base
context`.

Note the `[Syscall TODO]`: with the invocation stranded, `hasInvocation()` latches and the guest

## Two of the test's own failures were the test's fault, and are recorded as such

Both were found while building this and are worth keeping, because they are traps:

1. **A caller that republishes its own entry is restarted from the top.** The first version of the
   test caller set `ctx->pc` to the function entry before the syscall, so re-entry ran the prologue
   again and `s2`/`s3` reset *for a different reason*. Generated code does not do this: it publishes
   a distinct resume entry (`label_10286dc`) that the re-entry lands on. The test now has a separate
   resume function, and says why.
2. **A driver holding its own context copy is the same class of bug.** The test drove a private
   `env.ctx`, so `serviceInvocations()`'s published context went nowhere. The test now drives
   `runtime.cpu()`, which is what the harness drives.
