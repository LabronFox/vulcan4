# G1.8c — W6 fell. The guest resumes; it no longer restarts itself.

Dish: `.auto/queue/31-g18c-resume-at-the-right-pc.txt` · commit: see `docs/HANDOFF.md`

---

## THE WALL (measured, not guessed)

From the G1.8b boot log:

```
pc=0x01000008   distinct_pcs=1   24 repeats
0x3c sce_SetupThread   calls=25
0x3d sce_SetupHeap     calls=25
0x40 sce_CreateSema    calls=50
distinct_mmio_addresses=0
```

`0x01000008` is the ELF **entry point**, and a guest loop does not re-initialise its own heap. The
guest was being **restarted from its entry** instead of resumed at the PC each frame published for
itself.

## THE HYPOTHESIS, STATED BEFORE THE RUN

The driver's context and the scheduler's `GuestThread::context` are **two copies** of the main frame.
`EeScheduler::run()` keeps the scheduler's copy current because `run()` is the only thing advancing
the guest. The harness is not `run()` — it advances `PS2Runtime::m_cpuContext` directly — so the
scheduler's copy goes stale. `serviceInvocations()` ended with `copyMainContextToRuntime()`,
publishing the **stale** copy over the **live** one.

**The evidence confirmed this and named it further than the hypothesis did.**

## 1. THE RED TEST

`G1.8c: a frame chain is entered once, and resumes at each frame's own published PC`

A chain of 4 frames. Each publishes the next resume PC, then makes an overridden syscall. The entry
frame seeds `$s2`/`$s3` **once** so the tail proves they survived every later link. Data-driven via
`$a3`, so there is no per-link copy of the function to go stale.

It asserts the mechanism, not just the symptom: the **entry is entered exactly once**, each link runs
exactly once, and **no frame was restarted from inside a link** (`gChainResumePcs` must stay empty —
reaching the line after `handleSyscall` at all means the frame was never resumed).

`links=256` is the step cap. The chain never advanced: it spun on `chainLink0` forever, calling the
override handler 256 times without ever reaching the tail.

## 3. THE MECHANISM, PROVEN BY PROBE — NOT BY READING

Reading the code said "stale copy". A temporary probe on the two PCs confirmed it:

```
    256 [PROBE] pre-copy  main.pc=0x00300808 runtime.pc=0x00300808
    256 [PROBE] post-copy runtime.pc=0x00300808
      7 [PROBE] pre-copy  main.pc=0x00300708 runtime.pc=0x00300708
```

**256 consecutive resumes, every one at `0x00300808`** — the PC the base frame held *before the
chain ever published a new one*. The probe was removed immediately after; it is not in the commit.

## 4. THE FIX

In `EeScheduler::serviceInvocations()`, **on entry**, before anything is serviced:

```cpp
if (!m_guestExecuting.load(std::memory_order_acquire))
{
    if (GuestThread *main = thread(kMainThreadId))
    {
        main->context = m_runtime.m_cpuContext;
    }
}
```

Three decisions, each forced by something measured:

- **Refresh BEFORE, not after.** `onComplete` writes the handler's `$v0` into the base frame, so
  refreshing afterwards would discard the very result being delivered. Refreshing first makes the
  frame correct, lets `onComplete` apply `$v0` to a correct frame, and the unconditional publish at
  the end then delivers both. (An earlier attempt refreshed after and the chain still lost `$v0`.)
- **Guarded on `m_guestExecuting`,** which is true only while `run()` is between its own steps — the
  one case where the scheduler's copy is authoritative. **An unguarded version hung the suite**;
  that was measured in G1.8b, and the guard exists because of it.
- **No special case for any address,** including `0x01000008`. The fix is a copy direction, not an
  address check.

## 5. GREEN, AND THE TEST DISCRIMINATES

```
  [Run]: G1.8c: a frame chain is entered once, and resumes at each frame's own published PC  [Passed]
Total Tests: 450   Passed: 450   Failed: 0
```

The discriminating mutation for this dish was applied *first*, before the fix existed: the test
failed with `links=256 tail=0` and passes with `links=4 tail=1`. Those two numbers are the whole
dish, and they are the same measurement in both directions.

### Two of the red assertions were the test's own fault, and are recorded as traps

1. **The entry frame also makes a syscall**, so a correct run has `K_CHAIN_LINKS + 1` links and
   handler calls, not `K_CHAIN_LINKS`. Asserting the naive count made a *correct* fix look wrong.
2. **Re-seeding `$s2`/`$$3` in every link re-seeds over its own evidence.** They are now seeded
   once at the entry, so the tail genuinely proves survival across all three links.

## 6. THE PRODUCT — W6 IS DEAD

```
VULCAN4 BOOT REPORT functions_entered=95 halt=guest_cycle_no_progress bios_files=0
VULCAN4 HARNESS detail=guest is cycling through 1 addresses and has reached no new one in 24 repeats
  (first 0x0x0100f800) pc=0x0100f800 distinct_pcs=50
  dispatcher_transfers=5 serviced_invocations=5
```

| | before (W6) | after (G1.8c) |
|---|---|---|
| `functions_entered` | 25 | **95** |
| `distinct_pcs` | 1 | **50** |
| cycle address | `0x01000008` (ELF entry) | **`0x0100f800`** |
| `sce_SetupThread` | **25** | **1** |
| `sce_SetupHeap` | **25** | **1** |
| `sce_FindAddress` | 25 | **2** |
| `distinct_mmio_addresses` | **0** | **228** |
| `total_syscall_calls` | 175 | 77 |

**The guest's CRT init now runs once, not 25 times.** That is W6 dead, measured.

**And the guest now touches hardware: 228 distinct registers, 292 accesses.** 195 of them in
`0x7000xxxx` — the GS/GIF DRAM window. **The guest is writing to the Graphics Synthesizer.**

### The dish's own gate, honestly

```
best: functions_entered=95 halt=guest_cycle_no_progress | distinct_pcs 50
GATE_EXIT=1
```

**The gate is NOT met, and not because the fix failed.** The gate demands the halt stop being
`guest_cycle_no_progress`; it has not, because the guest **still cycles — at a different place.**
`distinct_pcs` went 1 → 50 and the cycle address moved off the entry point, so the gate's `n > 25`
and `dp > 1` conditions both pass and only the halt condition fails. Per the dish's own step 5 this
is **"the wall has moved"**, and a named next wall is a win, not a failure.

## 7. THE NEW WALL — W7, named from the measurement

The guest spins in a **byte-at-a-time store loop**:

```
0x100f800:  sb    $v0, 0x0($t1)      // WRITE8(t1, v0)
0x100f804:  addiu $t1, $t1, 0x1
0x100f808:  bne   $t1, $t4, 0x100f808 // loop while t1 != t4
```

That is the shape of a **memset/memcpy tail**, or a DMA-adjacent fill, writing toward
`0x7000xxxx`. It never terminates because `$t4` (the end pointer) is not what the loop expects —
most likely `$t1` ran past `$t4` unsigned, or `$t4` was never set because the address it came from
was published by a frame we resumed incorrectly. **This is the next dish, and it is the first wall
whose fix has a path to milestone 2 (`VULCAN4 FRAME source=guest`)**, because the guest is already
writing to GS memory.
