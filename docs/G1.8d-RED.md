# G1.8d-RED — W8: the guest's triangles are being thrown away by a depth test nobody enabled

## The headline

**The wall is not the guest. It is our own GS, and the defect was predicted one dish ago.**

Gran Turismo 4 submits `PRIM=3` — a real triangle, 174 times — writes the whole transfer block
(`BITBLTBUF`/`TRXPOS`/`TRXREG`/`TRXDIR`), and **never writes `TEST_1` (0x47)**. On real hardware
that is fine: the depth test is gated on `TEST` bit 16 (`ZTE`), so with `ZTE` clear it is
**disabled** and pixels are written. Our runtime reads `ZTEST` **unconditionally**, so `TEST == 0`
means `ZTEST` method 0 = **NEVER**, and **every pixel is discarded** — silently, with no error.

This was named at **G2.4** in `docs/LIMITATIONS.md` under *"ZTE is not honoured"*, on the evidence
that our own probe's `TEST_1=0` drew nothing. The real guest has now arrived at exactly that
prediction. This is the same class of defect the project keeps meeting: **something earlier did not
happen**, and the symptom appears somewhere else entirely.

## Fix 1 (shipped): the cycle is now decoded, not just counted

`PS2GuestProgress::history()` already held the cycle; the harness simply never decoded it on the
cycle-halt path — only on the deadline path. The decoder is now shared, so a cycle halt prints every
instruction in the block and, for each load, **the address it polls and the value sitting there**:

```
VULCAN4 CYCLE pc=0x… block_instructions=N history_len=…
VULCAN4 CYCLELOOP pc=0x… insn=0x… <mnemonic>  -> POLLS addr=0x… value=0x…
VULCAN4 CYCLEDEPENDS on: 0x… 0x…
```

This is the same principle as W7's nine retracted hypotheses: *a symptom is not a blocker until it
has an address.*

## Fix 2 (shipped): the cycle detector was DEAD CODE

Before the above could print anything, the detector had to fire — and it could not. Measured on a
**20,000,000-entry** boot with `distinct_pcs` frozen at 112: **zero** `VULCAN4 CYCLE` lines. Every
`guest_cycle_no_progress` halt in `run/` came from an older build.

The cause was in the harness's own wiring:

```cpp
const bool reachedNewCode = (functionsEntered != progressFunctionMark) || (mmio != mark);
progressFunctionMark = functionsEntered;          // <- assigned the value just compared against
```

`functionsEntered` advances on every entry, so `reachedNewCode` was a constant **`true`**,
`PS2GuestProgress::observe()` reset `m_repeats` on every PC, and the threshold could never be
reached. **A hang detector that cannot detect a hang** — and it was the reason the state on disk
read `entry_budget_exhausted` at 20M entries instead of naming a wall.

The correct signal is what the brief's own comment says: *"reaching code this guest has not run
before"*. That is the **distinct PC count**, which the harness already tracks. Fixed to compare
`distinctPcs` growth, and the detector now fires — at **44,579** entries, roughly 450× earlier than
the budget it previously ran into:

```
VULCAN4 BOOT REPORT functions_entered=44579 halt=guest_cycle_no_progress bios_files=0
VULCAN4 HARNESS detail=guest is cycling through 5 addresses ... in 4096 repeats:
  [0x01027e98 0x01027c70 0x01027eac 0x0100076c 0x01000760 ] -- decoded on the VULCAN4 CYCLELOOP lines
```

**This is the answer to the brief's step 5 for a partial win:** the loop terminates, the guest enters
an entirely new region (`0x010007xx`, no longer W7's `0x0100f8xx`), and the new cycle address is
named — `0x01000760`, five addresses wide.

## Fix 3 (attempted, REVERTED): honour ZTE

The fix in `GSCpuBackend::WritePixel` is four lines — gate the Z test on `ZTE`:

```cpp
const bool zteEnabled = ((ctx.test >> 16) & 0x1u) != 0u;
bool zpass = true;
if (zteEnabled) { zpass = false; switch (ztestMethod) { … } }
```

**It worked.** The RED test went green: with `TEST_1` at its reset value `0`, the triangle rasterised
instead of writing 0 pixels.

**It also broke three previously-passing depth assertions**, and I did not explain that within this
dish's budget:

- `a passing CT32 DATE should allow depth`
- `CT24 DATE should not block depth`
- `AFAIL=ZB_ONLY should update depth`

**The runtime change was reverted rather than shipped.** A fix that breaks a passing test is the old
bug back, and the brief is explicit about not regressing what works. Shipping a half-understood depth
change to reach a milestone would be exactly the kind of plausible-looking wrong answer this project
has been bitten by repeatedly.

The RED test is kept at `tools/patches/ps2recomp-linux-g18d-zte-red.patch`, **deliberately not
applied** — a failing test in the suite is worse than no test, and this one is evidence, not a gate.

## A second, separate finding

**`VULCAN4 FRAME source=guest` does not exist in this codebase.** `grep -rn` over `tools/` returns
nothing. The brief names it as the finish line and says to emit it "if guest GIF data reaches the
draw path" — but there is no code that could ever emit it, and **no log in `run/` contains it**. The
milestone is currently unreachable by construction, independent of any GS bug. The guest's GIF
traffic *does* arrive (`[gs:gif]` shows 9 packets, including one of 114,688 bytes, plus
`PRIM=3` triangle submissions), so the marker needs writing as well as the depth fix.

## A retraction: "five NOPs" was NOT supported

The first run of the new decoder printed `insn=0x0  sll` for all five cycle addresses, which reads as
"the guest is spinning in a five-NOP trap". **That reading is wrong and is retracted.** The decoder
indexes the harness's RDRAM by the low 24 bits of the guest vaddr, which does not reproduce the ELF's
mapping (`PT_LOAD` vaddr `0x01000000`, file offset `0x1000`), so it reads zeroed RDRAM for *every*
address and prints a mnemonic for a word it never actually fetched.

Checked against `SCUS_973.28` directly:

```
0x01000754: 24060003  addiu $a2, $zero, 3
0x01000758: 0220202d  dadddu ...
0x0100075c: 00000000  nop            <- a REAL nop, from the ELF
0x01000760: 0000282d  dadddu ...     <- the cycle address; NOT zero
```

So the honest statement is: **the cycle is five addresses wide and its instructions are not yet
decoded.** The decoder now labels a zero word `[UNVERIFIED ...]` instead of printing `nop`, so this
cannot be mistaken for a finding again. Fixing the mapping properly (decode through the ELF, or
teach the harness RDRAM's real base) is the next session's first line of work — and it is worth
saying that a five-address cycle in which **none** of the five is a branch is itself the interesting
clue, since `loads=0 branches=0` means the closing branch is not among the sampled addresses.

## Method note

This wall took **one** pass to name, after ten passes on W7 spent walking function by function. The
generalisation, and the third time it has paid: **when the guest is waiting on hardware, read what
the guest wrote, not what our code did with it.** The answer was in a register the guest never
writes.

## THE GATE IS NOT MET. Here is exactly why, in numbers.

```
best: functions_entered=44579 halt=guest_cycle_no_progress | distinct_pcs 112 | guest_frame False
GATE: FAIL
```

The gate passes if **the frame marker is present**, **or** `functions_entered > 95` **and** the halt is
not `guest_cycle_no_progress`. One clause and half of the other:

| clause | result |
|---|---|
| `functions_entered > 95` | **44579 — satisfied**, and 450× higher than the 95 the brief described |
| halt `!= guest_cycle_no_progress` | **fails** — the guest is genuinely cycling, now named |
| `VULCAN4 FRAME source=guest` | **impossible** — the string does not exist in this codebase |

**I did not meet this gate and I am not going to argue around it.** What this dish did is name the
wall, fix two of our own bugs, and produce the evidence for the third. Breaking a guest that is
correctly identified as stuck would take either the ZTE fix — which regressed three depth tests I
could not explain — or a frame marker that has to be written from scratch.

**Two gate observations worth recording, since they will confuse the next reader:**

1. **The gate sorts log filenames alphabetically, not by mtime.** There are 85 logs in `run/`; it
   reads the last six *by name* — `boot_w7k.log`, `boot_w7probe.log`, `longrun.log`, `probe16.log`,
   `trace.log`, `trace_all.log` — all of them stale. Every `boot_G18*` proof log from this session
   sorts into the middle and is invisible to it. The evidence run was copied to
   `run/zz_G18D_PROOF.log` so it is at least readable. **This is a defect in the gate, not a pass**,
   and it means a green verdict from it should be treated with suspicion until fixed.
2. **`boot_G18F2.log` would have passed the gate dishonestly** — 20,000,000 entries with halt
   `entry_budget_exhausted`, from *before* the dead-detector fix. That run had 20M entries because
   the detector could not fire, not because the guest was healthier. Do not read it as progress.
